# Architecture decisions

## ADR-001: Venue-scoped first release

Decision: Start with one venue.

Reason: A venue-specific policy test needs less identity, governance, and integration complexity than a cross-venue hub.

## ADR-002: Batch data first

Decision: Start with file or controlled batch intake.

Reason: Batch intake supports data-quality review, reproducible runs, and a faster design-partner pilot.

## ADR-003: Transparent baseline first

Decision: Start with transparent behavioral summaries and seeded simulation.

Reason: Customer review needs traceable calculations before advanced modeling.

## ADR-004: No direct PII in analytics

Decision: Reject direct PII fields.

Reason: The first product needs a clear privacy boundary and tokenized records.

## ADR-005: Synthetic demo before customer data

Decision: Build a full local demo with synthetic events.

Reason: Engineering progress must continue while data access and legal review remain open.

## ADR-006: Next.js and Neon for the first hosted slice

Decision: Use Next.js route handlers on Vercel with Neon PostgreSQL and Neon Managed Auth.

Reason: One application boundary keeps the first pilot small. Neon supplies hosted relational storage and the authentication boundary. Long-running validation and report jobs remain a separate follow-up service.

## ADR-007: Read-only venue adapter

Decision: Add public Polymarket market metadata reads without private credentials, order placement, or custody.

Reason: The pilot tests evidence workflows. Execution adds financial, legal, and operational risk before customer value is proven.

Source: [Polymarket Gamma API documentation](https://gamma-api.polymarket.com/docs).

## ADR-008: Holdout model remains separate from product scoring

Decision: Keep the Jan-Mar 2026 model evaluation in the analysis package and outside production customer scoring until independent review.

Reason: The public-data result is observational and uses a mark-to-market proxy. Production use needs customer validation, model governance, and documented intervention rules.

## ADR-009: Stake response and within-session escalation use separate trades

Decision: In `behavior-0.2.0`, signal 1 (post-outcome stake response) and signal 6 (escalation within session) never use the same post-loss trade.

- Signal 1 takes the first trade after a realized loss. If that loss is the second or later loss of a losing run, and the next trade is in the same session, the trade belongs to signal 6 instead.
- Signal 6 starts from the second loss in a run. It measures stake growth per additional consecutive loss, relative to the stake on the trade after the first loss. The value is exp of the least-squares slope through the origin of log(stake after loss m ÷ stake after loss 1) on (m − 1).

Reason: The v0.2 simulator multiplies the two: next stake = base stake × chase multiplier × escalation. Suppose signal 1 also used trades deep inside losing runs. Then an escalating trader's chase multiplier would already contain escalation, and the simulator would count it twice. With separate trades, chase is the response to one loss, and escalation is the extra growth per additional loss in the same session.

Consequences:

- A losing run ends at a session boundary, which matches the simulator's "consecutive losses this session" rule. The first trade of a new session after a loss counts toward signal 1, even if the previous session ended on a long losing run.
- Traders with long losing runs have fewer signal-1 episodes. The trades excluded from signal 1 are counted in `postOutcomeStake.excluded.escalationPosition`.
- Re-entry latency (signal 2) is not split this way, because the simulator draws latency from the last outcome only.

## ADR-010: Behavioral synthetic generator rules the estimator must account for

Decision: `behavioral-synthetic-0.1.0` (`src/synthetic/behavioral-generate.mjs`) simulates SYNTHETIC traders with parameters defined against `behavior-0.2.0`. Full rules are in `docs/BEHAVIORAL-SYNTHETIC.md`. These choices affect how twin-0.2.0 should estimate parameters and how recovery tests should compare estimates with the truth:

1. Every noise term is lognormal with median 1. Money and time parameters are medians. Chase and escalation multiply the stake, so estimate them on the log scale: `postOutcomeStake.lossMinusWin.logRatioDifference` for chase, `escalation.logSlope` for escalation.
2. Running out of money ends the session; the stake is never capped at the balance. Stakes stay undistorted, but observed stop rates include these forced stops, mostly in the down buckets. The truth file records forced stops by bucket, separately from hazard stops. *Corrected in Prompt 3:* this ADR used to say a recovery test could compare a stop-rate estimate with hazard plus forced stops. Those counts come from the same trades the estimator sees, so hazard plus forced stops per trade is a sample proportion, not a parameter, and coverage measured against it means nothing. It is a descriptive check only. twin-0.2.0 estimates the voluntary hazard and is checked against `stopHazard` (ADR-011).
3. The generator's drawdown buckets and low-balance threshold use the trader's `baseStake`. The signals use the observed median stake. For chasers and shrinkers the two differ, so bucketed stop rates and low-balance triggers don't line up exactly.
4. Refuel deposits always land inside the refuel window and inside the session. A new session starts at least max(`sessionGapMinutes`, `refuelWindowMinutes`) + 1 minute after the previous session's last event, so a session-start deposit is never counted as a refuel. Signal 5 therefore counts the generator's refuels, except in the rare case where a later trigger's refuel falls within 60 minutes of an earlier trigger that didn't refuel.
5. Within-session latency is clamped to between 2 seconds and `sessionGapMinutes`, so the signals see exactly the generator's sessions. The latency parameters match `reentryLatency.withinSession`, not `anySession`. The observed session rate is below `sessionsPerDay`, because idle time = `minIdle` + Exponential(1440 / `sessionsPerDay` minutes) is measured from the end of the previous session.
6. Blanked outcomes are missing completely at random, after simulation. The trader reacted to the true outcome, so a blanked loss still drives the next stake's chase term. The signals see a missing outcome, which breaks the losing run there.
7. The archetypes and the population have a negative edge of about 9% of stake per trade, so balances run low and deposits recur. This is a modelling convenience, not a claim about any venue.

Reason: The generator exists to test parameter recovery. Each parameter should leave its footprint in one signal, and the generator and the signals should agree on sessions, outcomes, and balances. Where something leaks from one parameter into another signal (forced stops into stop rates, `baseStake` against median-stake edges), the leak is recorded in the truth file rather than hidden.

Consequences:

- Recovery tests should compare like with like: within-session latency with the latency parameters, and a voluntary stop-hazard estimate with `stopHazard`. Hazard plus forced stops per trade is a descriptive check only (corrected in Prompt 3).
- Signals are tested for direction only in Prompt 2. Exact recovery, with intervals and shrinkage, is Prompt 3's job.
- The population distributions are modelling assumptions, loosely informed by the OBSERVATIONAL Polymarket follow-up. They are not a calibration.

## ADR-011: twin-0.2.0 parameter estimation

Decision: `estimateTwins` in `src/engine/estimate.mjs` (model version `twin-0.2.0`) fits a small set of interpretable behavioral parameters per trader, each with a point estimate, a 90% interval, a sample size n, a shrinkage weight, and a status. Method and field needs are in `docs/MODEL_CARD.md`. These are the choices behind it.

1. **Inputs.** The estimator reads only `buildBehaviorObservations` (behavior-0.2.0), so it reuses the signal definitions instead of copying them. It never reads market or contract fields. The caller must pass a data label (SYNTHETIC, OBSERVATIONAL, or CUSTOMER), and every output carries it.
2. **Parameters are defined the way the Prompt 4 simulator will use them.** Next stake = `baseStake` × `chaseCoefficient` (after a realized loss) × `escalationPerLoss`^(k − 1) (after the k-th consecutive loss in a session) × lognormal noise with SD `stakeDispersion`. `baseStake` comes from trades with neither term: the trader's first trade, and trades after a realized win or push.
3. **Priors are fitted on the same dataset.** Each parameter's population prior is fitted by the method of moments to every trader's raw estimate in the dataset being fitted, with the sampling noise taken out (DerSimonian-Laird for normal and beta priors, a moment match for the idle-time prior). Every trader's data therefore informs both its own estimate and, as one of many, the prior. That is standard empirical Bayes. It needs enough traders: with fewer than 3 traders with observations there is no prior, estimates are unpooled (weight 1), and traders without observations are not estimable. Priors are stored once per dataset and model version (`twin_population_priors`), and a new dataset gets new priors. A prior fitted on customer data is customer-derived data and stays out of the repo. The prior's own estimation error is ignored, so intervals are slightly too narrow when few traders inform a prior.
4. **How intervals are computed.** All are equal-tailed 90% intervals of the posterior. Normal-normal (log scale): posterior mean ± 1.645 posterior SD, exponentiated. Beta-binomial: the 5th and 95th percentiles of the Beta posterior, by bisection on the regularized incomplete beta function. Inverse-gamma (idle time): the 5th and 95th percentiles of the posterior, from gamma quantiles, plus `sessionGapMinutes`. A trader's own sampling variance uses a moderated spread: the trader's sample variance averaged with the pooled within-trader variance, which counts as 5 observations. One or two noisy values then can't produce a falsely tight interval.
5. **Escalation is clustered by run through its shared reference stake.** Signal-6 points from one losing run all divide by the same stake (the one after the run's first loss), so they share its noise. The variance of the slope is σ² Σ_runs (Σx² + (Σx)²) / (Σx²)², with σ the trader's estimated `stakeDispersion`. We also tried a cluster-robust sandwich (CR1) and a jackknife over runs. Both ran too small on synthetic recovery, because a few long losing runs carry most of the leverage, so intervals built on them were too narrow.
6. **Latency truncation.** A within-session latency can't exceed `sessionGapMinutes`, because a longer gap starts a new session; the generator clamps at the gap. The mean of log latency is biased low for slow traders, so the raw estimate is the median log latency, with spread from the MAD and sampling variance (π/2) σ² / n. Neither moves while fewer than half the latencies reach the gap. A trader whose median latency is near the gap is underestimated.
7. **Voluntary versus all-cause stopHazard.** Prompt 4's simulator has its own broke rule, so twin-0.2.0 estimates the voluntary hazard. With balance fields on every trade, a trade is left out of the stop sample when the chance that the next stake exceeds the money available for it (balance after the trade, plus any deposit before the next trade) is at least 5%. The next stake is baseStake × the chase and escalation terms the trade implies, with lognormal noise `stakeDispersion`. The number of trades and stops left out is reported (`stopSample`). The rule depends only on the state before the stop decision, so it doesn't bias the hazard. The recovery test checks that it removes nearly all the forced stops recorded in the truth file. Without balance fields, the two causes can't be separated. The rate is all-cause, flagged `includesForcedStops`, and with the simulator's own broke rule it double-counts running out of money, so simulated stopping is overstated in low-balance states. Prompt 4 must label runs that use an all-cause hazard.
8. **Bucket edges and the low-balance threshold use the estimated baseStake**, not the observed median stake. That is what the generator does, and what the simulator will do. Running results are re-bucketed from the observations with `drawdownBucket`.
9. **Stop propensity.** Bucket hazards move together, and how often a trader reaches a bucket depends on the hazards themselves: a trader who quits early when a little down rarely reaches a large drawdown. Independent per-bucket priors were therefore fitted mostly to traders who don't quit, and were too low for down_large, worst for traders with no down_large trades at all. Each bucket's beta prior is now centered at the bucket rate × the trader's stop propensity, estimated from the trader's stops in the other three buckets (indirect standardization: observed over expected stops, shrunk toward 1 with a gamma prior fitted by the method of moments). Bucket rates are refitted against propensity-weighted exposure, which corrects for who reaches each bucket. The prior keeps the bucket's full fitted spread, so the propensity only moves its center. The update is still beta-binomial per bucket.
10. **Beta prior centers are the pooled proportion.** Re-weighting the center by 1 / (sampling variance + τ²), as the normal prior does, was tried and made stop and refuel coverage worse, because trial counts there depend on the parameter.
11. **Refuel needs balance fields.** `refuelProbability` uses signal 5's low-balance trigger with threshold `lowBalanceStakeMultiple` × the estimated `baseStake`. Without balances it is not estimable, and there is no prior to fall back on when no trader has balances. `refuelAfterLosingStreak` is reported separately as a labelled proxy (`proxyFor: refuelProbability`). It uses a different trigger, so it is not the same quantity. When balances are missing, Prompt 4 should switch its refuel trigger to the losing-streak rule and use `refuelAfterLosingStreak` as that trigger's probability. It must never apply the proxy to the low-balance trigger, and reports must say refuel behavior is proxied. Refuel trigger counts also depend on the refuel rate (a refuel restarts the low-balance cycle), which pulls the prior toward frequent refuelers.
12. **Idle time.** The mean idle time between sessions (last event to next first event) is fitted as `sessionGapMinutes` plus an exponential excess with an inverse-gamma prior. The excess is positive by definition, so the offset needs no generator constant. One-session traders get the prior. On a fixed window, long gaps near the end are cut off, so a real-data estimate is biased low.
13. **Statuses.** `estimated`; `prior_only` (inputs present, no observations for this trader: weight 0, the trader's prior); `not_estimable` (inputs missing, with a reason). A not-estimable parameter carries the population prior as `fallback` only when other traders in the same dataset had the inputs. Otherwise `fallback` is null.

Reason: The twin has to be an econometric model a reviewer can check by hand: a few named parameters, each fitted by a standard, one-paragraph formula, with honest uncertainty, and with short histories pulled toward the population rather than taken at face value. Recovery on SYNTHETIC traders with known parameters (`test/twin-recovery.test.mjs`) checks correlation, interval coverage, shrinkage, and the not-estimable paths. Its numbers stay in test thresholds and in the gitignored output of `npm run twin:recovery`.

Consequences:

- A missing realized outcome breaks a losing run in the signals, so a later trade can enter the chase sample with an escalated stake. With many missing outcomes, chase is biased in the direction of the trader's escalation.
- Synthetic population shapes matter for coverage. A population that is uniform with no tails (the generator's flat-bucket hazard) is over-covered when intervals are dominated by the prior.
- Prompt 4 should draw each run's parameters from the stored posterior (`posterior` on every parameter), not from the interval endpoints.
- The schema stores twin-0.2.0 parameters through the additive migration `db/migrations/0001_twin_v02_parameters.sql`.

## ADR-012: State-dependent simulator (simulator-0.2.0) and twin-0.2.1

Decision: `simulateTwinV2` in `src/engine/simulate.mjs` (simulator version `simulator-0.2.0`) simulates twin-0.2.1 twins trade by trade, with many seeded replicates per trader, and returns the median and the 10th and 90th percentiles of harm and activity metrics per trader and for the population. It implements the parameter definitions of ADR-011 point 2 exactly. `simulateTwin` is unchanged and kept as baseline-0.1 (`simulateBaseline` labels its output). Method and limits are in `docs/MODEL_CARD.md`. These are the choices behind it.

1. **Posterior draws, independent across parameters.** Parameters come only from the `estimateTwins` fit. Each run draws every parameter once, at its start, from the stored `posterior`: exp(N(mean, sd)) for log-scale normals, Beta(a, b) for probabilities, `offsetMinutes` + scale / Gamma(shape) for the idle time, with seeded samplers in `stats.mjs`. It never draws from interval endpoints. Only marginal posteriors are stored, so the draws are independent. The stop-hazard buckets were fitted with a shared stop propensity (ADR-011 point 9), so independent bucket draws ignore that correlation; this is a stated limit. If a drawn `winRate` + `pushRate` exceeds 1, both are rescaled to sum to 1 and the run is counted. With uncertainty off, runs use the stored estimates (the posterior centers).
2. **Statuses and simulability.** `estimated` and `prior_only` draw from `posterior`. `not_estimable` with a `fallback` draws from the fallback, recorded as "population prior, not this trader". `not_estimable` without one switches the mechanism off, and the result says which and why; nothing is filled with zero or a default. The base rule is that a trader can't be simulated without `baseStake`, `winRate`, and the latencies. We apply it to their whole mechanisms (stake: `baseStake`, `stakeDispersion`; outcomes: `winRate`, `pushRate`, `payoutMultiple`, `payoutSpread`; latency: both latencies and `latencySpread`) and add stops (every `stopHazard` bucket) and sessions (`meanIdleMinutes`), because without them a session or a horizon can't end. These share inputs with the named parameters, so in practice they differ only in tiny datasets with no prior. Chase, escalation, deposits, and refuel can be switched off. A trader with no realized outcome at all is not simulable even when fallbacks exist, because every outcome-driven parameter would be the population's, not the trader's.
3. **Stop basis.** With balance fields in training the hazard is voluntary, and the simulator's broke rule adds forced stops. Without them the hazard is all-cause and already includes running out of money. The broke rule can't be dropped, because a simulated balance can't go negative, so stopping is double-counted in low-balance states. We simulate anyway and label the runs `stopBasis: 'all-cause'`, with the double count in the trader's assumptions.
4. **Refuel proxy switch (ADR-011 point 11).** When `refuelProbability` is not estimable, the refuel trigger becomes `losingStreakLength` consecutive realized losses (signal 5's losing-streak rule: across sessions, reset by a win, a push, or a deposit), with `refuelAfterLosingStreak` as its probability, labelled `refuelTrigger: 'losingStreak (proxy)'`. The proxy is never applied to the low-balance trigger. `refuelProbability`'s population fallback is not used in this case: it would replace this trader's own proxy evidence with other traders' low-balance behavior. If the proxy can't be simulated either, refuel is off.
5. **Starting balance.** The trader's last observed `balance_after`, when the caller supplies it in `startingBalances` (`lastObservedBalances(events)` computes it). An `estimateTwins` fit stores parameters, not balances, so the balance comes in as an option rather than as a new field on the fit. Without it the trader starts at 0 with the session-start deposit rule. The rule used is in the trader's assumptions, including when training had balances but none was supplied.
6. **Empirical loss ratios.** A loss's result is the stake times a ratio drawn from the trader's stored loss quantiles of result ÷ stake (`payoutDistribution.resultPerStake.losses`). Only five quantiles are stored, so the draw interpolates linearly between them and holds p10 and p90 in the tails. A trader with no observed losses loses the whole stake (ratio −1), recorded as an assumption. The synthetic generator always loses the whole stake; real exchange data may not.
7. **Idle-time shape.** Idle time between sessions is `sessionGapMinutes` + Exponential(`meanIdleMinutes` − `sessionGapMinutes`), the estimator's model (ADR-011 point 12), at least one second above the gap so the signals see the same sessions. The generator uses minIdle + Exponential: the same mean, a different shape. Idle time moves timing only, so the reproduce check compares per-session and per-trade metrics, and uses refuel deposits rather than deposits after a loss, which a short simulated idle time can add to.
8. **Separate random streams for common random numbers.** Each kind of decision has its own stream, seeded from the run seed `stableSeed(seed:traderToken:replicate)`: outcomes (4 draws per trade), stake noise (2 per intended stake), latency (2 per trade, drawn even when the session ends), stops (1 per trade), refuel (2 per trigger), deposits (2 per intended deposit), and idle time (2 per session). Every parameter has its own sub-stream. A policy that changes one decision therefore never shifts another decision's draws, and Prompt 5 can compare policy and no-policy runs on common random numbers. `reseedStreams` re-seeds one stream for the check. A replicate doesn't depend on which other traders are simulated.
9. **Generator rules where the twin has no estimate** (`docs/BEHAVIORAL-SYNTHETIC.md`): the first session starts at a uniform time within 24 hours of the start; the session-start deposit rule (a balance below `lowBalanceStakeMultiple` × `baseStake` or below the first stake), raised to cover the first stake if short, with the first trade 1 to 5 minutes later; the refuel deposit lands between the trigger trade and the next trade, or 1 minute to min(`sessionGapMinutes`, `refuelWindowMinutes`) after it when the session ends; the broke rule ends a session instead of capping the stake; latency is rounded to whole seconds and clamped to [2 s, `sessionGapMinutes`]; stakes and wins are at least 1 cent; and the `maxTradesPerSession` cap (200). `GENERATOR_RULES` holds the constants, and a test checks them against the generator's.
10. **Why twin-0.2.1 adds `latencySpread` and `depositSpread`.** twin-0.2.0 had no latency noise and no deposit noise, and the simulator needs both. Zero noise would be a default, and the generator's values aren't estimates. Both use normal-normal shrinkage on log SD, with statuses, n, weights, intervals, posteriors, and fallbacks like every other parameter. `depositSpread` is fitted like `stakeDispersion`, on the log deposit amounts. `latencySpread` has to be robust to truncation at `sessionGapMinutes`, so it is MAD-based: each side's within-session log latencies (after a loss, after a win) are centered at that side's median observation (the lower middle one for an even count), which is left out, and the spread is 1.4826 × the median absolute deviation of the rest, pooled over both sides, with Var(log SD) = 1.3605 / n. It doesn't move while the gap stays above each side's upper quartile. We checked the alternatives by simulation: the plain MAD (with the median's zero deviation) is biased low on the log scale at the sample sizes most traders have, by an amount that depends on whether each side's count is odd or even; the median-pairwise-difference (Shamos) spread is unbiased and more efficient, but latencies cut off at the gap pull it down. Both spreads are in the recovery output. `latencySpread`'s coverage is asserted; `depositSpread`'s isn't, because it sits near the upper edge of the band, with many prior-only intervals (traders with fewer than 2 deposits).
11. **One hook for Prompt 5.** `intervention(point, proposal, state)` is called before a stake, before a deposit, and after a trade. simulator-0.2.0 always uses `NO_INTERVENTION` (the call is skipped) and implements no policy. ADR-013 extends the contract for the policy layer; runs with no policy are unchanged.
12. **Metrics.** A chase episode is a stake of at least 1.25 × the run's drawn `baseStake` on the trade after a realized loss. Stake noise alone crosses that line, so the same count after wins is reported as the noise floor. Deposits after a loss count every deposit within `refuelWindowMinutes` after a realized loss. Population bands sum each replicate across traders first (drawdowns are averaged), then take percentiles; percentiles of per-trader percentiles would not be a population distribution. `metricsFromEvents` computes the event-observable metrics from analytical events through `buildBehaviorObservations`, and a test checks it against the simulator's own counts on the same runs.
13. **The reproduce check.** `src/synthetic/truth-twins.mjs` builds twins from the generator's truth as point masses (`{ family: 'point' }`, a family `estimateTwins` never produces), with `meanIdleMinutes` = minIdle + 1440 / `sessionsPerDay`. Each trader is simulated for its training session count with uncertainty off, and we count the traders whose observed training value (from the events, or from the truth file for forced stops and refuel deposits) falls inside the simulated 10th-90th percentile band. The same check on fitted twins with uncertainty on is in-sample. Thresholds are stated in `test/simulation-calibration.test.mjs`; the numbers stay in test thresholds and gitignored output.

Reason: The twin has to react to what just happened and to a policy, which an outcome-independent simulator can't do. Every mechanism maps to one named twin parameter with its own uncertainty, every assumption the twin can't estimate is listed with the result, and the randomness is arranged so a policy comparison isolates the policy.

Consequences:

- Simulated runs from a CUSTOMER fit are customer-derived data and stay out of the repo, like the fit.
- Bands carry parameter uncertainty only as far as the marginal posteriors do; correlated uncertainty (stop propensity, base stake with dispersion) is not represented.
- The calibration check shows the simulator implements the model on SYNTHETIC data. Whether the model predicts traders' later behavior is the held-out validation (ADR-014).
- Prompt 5 adds policies through the hook and must keep each policy's effects to the decisions it changes, so common random numbers still hold.

## ADR-013: Policies with explicit response assumptions (policy-0.2.0)

Decision: `src/engine/policy-sim.mjs` (policy version `policy-0.2.0`) runs four policies on `simulateTwinV2` through its intervention hook. It compares each policy run with a no-policy run on common random numbers, and sweeps both the policy setting and named assumptions about how traders respond. `comparePolicyV2` runs one policy with one set of assumptions. `runPolicySweep` runs the sweep. `npm run policy:sweep` runs the default sweep on a SYNTHETIC behavioral population and writes to gitignored `analysis/output/policy-sweep/`. Runs with no policy are exactly simulator-0.2.0's, so the simulator keeps its version, and the policy layer carries its own. The baseline-0.1 layer (`validatePolicy`, `comparePolicy`) is unchanged, and its output is now labelled `simulatorVersion: 'baseline-0.1'`. There is no intervention data, so every response is an assumption, swept across a range and shown with every result. Results are simulations under stated assumptions: never causal claims, and never a recommendation to act on any trader. Method and limits are in `docs/MODEL_CARD.md`.

1. **The hook contract.** A policy acts only through `intervention(point, proposal, state)`. The contract is extended as narrowly as the four policies need. Each return is checked, and a bad one throws.
   - `sessionStart` (new): `{ seconds, earliestSeconds, lastEventSeconds }` → `{ seconds, depositCents? }`. The start can move later (a cooldown, leaving for the day) or earlier (a quick return), but never before `earliestSeconds`, which is more than `sessionGapMinutes` after the last event. Event data therefore always sees a new session. `depositCents` lands a deferred deposit at the start.
   - `beforeStake`: `{ stakeCents }` → `{ stakeCents }` or `{ skip: true }`.
   - `beforeDeposit`: `{ kind, amountCents, seconds }` → `{ amountCents }`, from 0 up to the proposed amount. `kind` is `sessionStart`, `refuel`, or `deferred`. `seconds` is the deposit's own time, which a daily limit needs.
   - `afterTrade`: `{ endSession }` → `{ endSession, resumeAtSeconds?, reset? }`. The hook is called after the trader's own stop decision, and the proposal's `endSession` is that decision. A policy can't overrule it. When the trader stops, the session ends whatever the policy returns. Otherwise a policy can end the session (counted as an intervention stop) or pause it: the next attempt comes no earlier than `resumeAtSeconds`. `reset` makes the return a new session.
   - `INTERVENTION_POINTS` keeps simulator-0.2.0's three points, and `SESSION_START_POINT` is the new one. `prepareSimulation` and `simulateReplicate` are exported, so the policy layer runs exactly the code `simulateTwinV2` runs.
2. **Paired common random numbers.** For each trader and replicate, the policy run and the no-policy run share the run seed, the parameter draws, and every trader stream. The no-policy run is computed once per trader and replicate and reused for every cell. All policy and response randomness comes from a new `policy` stream. Like every stream, it is seeded by name from the run seed, so adding it moved no other stream. A policy never draws from a trader stream. Each policy uses a fixed number of policy-stream draws per event, whether or not the draw matters: cooldown 1 per trigger (leave), stake_limit 1 per over-cap attempt (resubmit), session_loss_limit 2 per limit hit (quick return and its time), deposit_limit none (the carryover is a share). Cells with different assumption values therefore share the same uniforms, so raising a probability never flips a decision the other way.
3. **Per-attempt draws.** An attempt is an intended stake that reaches the outcome: placed, capped, or skipped. Each attempt uses 4 outcome, 1 stop, and 2 latency draws, and the next intended stake uses 2 stake-noise draws. An attempt the broke rule ends uses none of these, as in simulator-0.2.0. Later attempts therefore line up with the baseline's attempt by attempt:
   - A capped stake keeps the attempt's own outcome draw, with the payout or loss ratio applied to the capped stake.
   - A skipped attempt places nothing and leaves the state unchanged. The trader then makes their own stop decision, with that attempt's stop draw at the unchanged bucket. If they don't stop, they try again after that attempt's latency for the last outcome. The session cap counts attempts, which equals trades in a run without skips. That cap ends a chain of skips.
   - A cooldown pause doesn't replace the trader's own stop decision: the stop draw comes first. The next attempt comes at the later of the latency and the end of the cooldown.
4. **Policies.** Thresholds are in currency, as an operator sets them, and they are the same for every trader. The default sweep settings are starting points to re-pick for a real dataset's scale.
   - `cooldown` (`durationMinutes`; `lossStreak`, default 3; `drawdownThreshold`, default none) pauses trading when the session first reaches `lossStreak` consecutive realized losses (the losing run escalation uses), or a drawdown of `drawdownThreshold`. It fires on the crossing of the combined condition, not again while the condition holds. Sweep: 5, 15, 30, and 60 minutes after 3 losses.
   - `deposit_limit` (`dailyLimit`) cuts any deposit that would take the UTC day's total past the limit. Sweep: 100, 250, 500.
   - `stake_limit` (`maxStake`). Sweep: 25, 50, 100.
   - `session_loss_limit` (`lossLimit`) ends the session after the trade that takes its drawdown (net of deposits) to the limit. Sweep: 50, 100, 200.
   - The type names are the baseline-0.1 layer's, plus `session_loss_limit`. One policy runs at a time.
5. **Response assumptions** (`RESPONSE_ASSUMPTIONS`). The ranges are assumptions for sensitivity, not estimates. Each default is the policy's rule applied as written, with no further response from the trader: a cooldown only delays, an over-cap stake is placed at the cap (Prompt 0's cap semantics), a blocked deposit is lost, and a forced end is followed by the normal idle time.

   | Assumption | Meaning | Default | Default range |
   | --- | --- | --- | --- |
   | `cooldown.reboundMultiplier` | Stake multiplier on the first `reboundTrades` trades after the trader returns. It ends early if that session ends. | 1 | 0.5, 1, 1.5 |
   | `cooldown.reboundTrades` | How many trades the rebound covers | 3 | 3 (not swept) |
   | `cooldown.leaveProbability` | Probability the trader leaves for the day instead of returning | 0 | 0, 0.25, 0.5 |
   | `cooldown.referencePoint` | `carry` or `reset` (point 6) | carry | carry, reset |
   | `stake_limit.resubmitProbability` | Probability of resubmitting at the cap rather than skipping the trade | 1 | 0, 0.5, 1 |
   | `deposit_limit.carryoverShare` | Share of the blocked amount deposited on a later UTC day | 0 | 0, 0.5, 1 |
   | `session_loss_limit.quickReturnProbability` | Probability of a new session within the hour rather than after the normal idle time | 0 | 0, 0.5, 1 |

   A response applies only when the policy actually interrupts the trader. If the trader stops on their own at a cooldown trigger or at the loss limit, nothing is drawn for leave, rebound, or quick return. The cooldown still blocks trading until it ends, so it can delay the next session.
6. **The reference point.** After a cooldown, `carry` keeps the session's running result, losing run, and drawdown, and the simulator keeps it as one session. A pause longer than `sessionGapMinutes` would show as two sessions in event data. The result counts these (`pausesLongerThanSessionGap`), and a test checks the event data agrees. `reset` makes the return a new session: running result, losing run, bucket, and drawdown start over, with no idle draw and no session-start deposit, so the trader streams stay aligned. A trader whose stop hazard rises with drawdown comes back in the flat bucket and can play longer than without the cooldown. Session drawdown also restarts at the return by definition, so under `reset` it falls even for a trader whose behavior doesn't change. Both values are swept.
7. **Edge cases.**
   - **Reduced first deposit.** A reduced session-start deposit can leave the first stake unaffordable. The run ends that session as a forced stop with no trade, and the session is not counted.
   - **Leaving for the day.** The next session starts no earlier than the next UTC midnight; then the trader's normal idle time runs from there. The start is the larger of the last event and midnight, plus the idle draw.
   - **Deferred deposits.** A deferred deposit lands at the start of the trader's first session on a later UTC day, before the session-start deposit rule. It passes through the limit, and any part blocked again is carried with the same share. Carried amounts not deposited by the horizon end are reported as `pendingCentsAtEnd`.
   - **Within an hour.** A quick return starts between `sessionGapMinutes` (strictly more, so the event data sees a new session) and 60 minutes after the session's last event, a refuel deposit included, uniformly from the policy stream. If the normal idle draw is sooner, the trader starts then.
   - **Horizon end.** An attempt that a pause pushes to or past the horizon end is not made, and the run ends.
8. **The money model.** `deposit_limit` applies only to traders with the money model. For the others it is not applicable: per-trader results are null, with a reason, and the population covers only the traders it applies to. It is never reported as a zero effect. Every result keeps the simulator's labels and lists all-cause-stop, proxy-refuel, money-off, and not-simulable traders (`labels`). A deposit limit on an all-cause trader inherits that trader's double-counted stopping in low-balance states.
9. **Harm, activity, and the primary pair.**
   - Every `SIMULATION_METRICS` harm metric gets a harm reduction, 1 − policy ÷ baseline. Every activity metric gets activity retained, policy ÷ baseline. Both come with paired differences in natural units.
   - Per trader, ratios are computed per replicate, then summarized (median, p10, p90). A zero baseline gives null, never 0 or 1. A pair where either run has no value is left out of that metric: a money metric without the money model, or a drawdown in a run with no session.
   - The population sums each replicate across traders first (it averages drawdowns, over the traders with a value in both runs), then takes the ratio, then the percentiles.
   - The default primary pair for the trade-off chart is total net loss (harm) against total stake (activity). Both are configurable through `primary`.
   - Net loss is the money the trader loses. It is a sum over trades, so it means the same thing whatever the session accounting. Session drawdown restarts at a `reset` return by definition, and the tests show it falling for a trader whose behavior doesn't change at all.
   - Under the synthetic negative edge, net loss falls roughly in proportion to stake. A policy that only cuts activity therefore also cuts net loss, and harm reduction alone would credit it. Plotting harm reduction against activity retained puts such a policy on the line harm reduction = 1 − activity retained. `beyondActivityCut`, the distance above that line per replicate, is what separates a policy that cuts loss more than play from one that only cuts play.
   - Points can still leave the line on synthetic data. Edges differ between traders, so a policy that cuts some traders' play more than others shifts the pooled ratio, and the money constraint caps what a trader with a deposit limit can lose.
   - Total stake is the activity measure because a stake cap leaves the trade count alone and cuts handle.
   - Session drawdown, chase episodes, and deposits after a loss are reported for every cell and can be made primary.
10. **Days horizon only.** Policy comparisons reject a session-count horizon. In a fixed number of sessions, the time a cooldown, a leave, or a delayed session takes away costs nothing, because the trader gets the same sessions later. In a days horizon it costs activity, which is the trade-off being measured.
11. **One-at-a-time by default, the full grid as an option.** The default design varies one assumption across its range with the others at their defaults, at every setting, and always includes the all-defaults cell. For the default settings that is 51 cells. The grid crosses every combination, 72 cells for the cooldown alone, and shows interactions the default design misses. Both designs give the chart's slices: for each assumption value, a series of points over the settings (harm reduction against activity retained for the primary pair, with p10 and p90 bands).
12. **The driver statement.** For each policy, the sweep compares two spreads of the primary harm reduction's population median. One is the spread across the settings, with the assumptions at their defaults. The other is each assumption's spread across its range, at the setting where it moves the result most. The sweep names the largest and writes a plain sentence (`driver.statement`). When an assumption wins, the sentence says the result is driven by an assumed response, not by an estimate.
13. **Bug fixed in the simulator.** After a session with no event, the next idle time was measured from the previous event, so the next session could start before the empty one, and a days horizon might never be reached. Only a policy can make such a session (a fully blocked deposit), so no-policy runs were never affected and still match simulator-0.2.0 byte for byte. Now the next idle time runs from the empty session's start. A regression test checks it.
14. **Findings the tests pin.** The numbers stay in test thresholds and gitignored output.
    - With rebound 1, nobody leaving, and `carry`, a cooldown is the baseline run delayed. In a days horizon it loses a suffix of attempts: trades, total stake, and chase episodes never rise in any paired run, and the population's median paired net-loss difference is at or below zero.
    - With rebound 2, the chaser's session drawdowns deepen and its forced stops rise. Its chase episodes don't rise, because the chaser's after-loss stakes (1.8 × base, with stake noise 0.2) nearly always clear the 1.25 × base line already, and the extra forced stops cut trades. For `steady`, whose after-loss stakes are not over the line, the same rebound raises chase episodes. A chase metric saturates for heavy chasers, so it understates what a rebound does to them.
    - With `reset`, a cooldown makes quits-when-down play longer on average, because the return puts it back on the flat bucket's stop hazard. Its average net loss rises too, though the paired median sits at zero and the band spans both signs. This is a finding about the assumption, not a bug.

Reason: The product's value is how traders respond to a policy, and there is no intervention data, so the honest model makes every response a named, swept assumption and keeps the policy's effects inside the decisions it changes. Pairing on common random numbers isolates the policy from luck. The harm-against-activity framing keeps a policy that only cuts play from looking like harm reduction. The driver statement says plainly when an assumption, rather than the policy, decides the result.

Consequences:

- Policy results from a CUSTOMER fit are customer-derived data and stay out of the repo, like the fit.
- Paired bands carry the twin's parameter uncertainty and process noise, not uncertainty about the responses. That uncertainty is shown only by the sweep.
- One-at-a-time sweeps miss interactions between assumptions (for example, reset with a rebound). Use the grid design to see them.
- The default sweep is (51 cells + 1 baseline) × traders × replicates runs. Its runtime is printed by `npm run policy:sweep`, and the script takes flags to scale it down.
- Prompt 7's chart reads `policies[].chart` and the per-trader rows. Groupings are by archetype or parameter range (each trader's estimates are in `traders`), never by individual token in a summary.

## ADR-014: Held-out validation (holdout-0.1.0)

Decision: `runHoldoutValidation` in `src/engine/holdout.mjs` (version `holdout-0.1.0`) fits twins on each trader's earlier data, simulates the later period, and compares what each model simulates with what the trader then did. It compares the twin (twin-0.2.1 on simulator-0.2.0) with baseline-0.1 and a naive model, and on SYNTHETIC data with a truth reference. `validateTwin` stays as it was, labelled a same-window mechanics check: it compares simulated totals with the window the profile was built from, so it validates nothing. `npm run twin:holdout` runs the validation on a SYNTHETIC behavioral population, with and without balance fields, and writes to gitignored `analysis/output/twin-holdout/`. Results are evidence about a model on stated data. They are never an accuracy headline and never a causal claim, and their numbers stay in test thresholds and gitignored output. Method and limits are in `docs/MODEL_CARD.md`.

1. **The split is time-based per trader, never random.** A trader's active period runs from their first to their last trade, deposit, or withdrawal. The cut is the start of the first session that starts at or after `trainShare` (default 0.75) of the way through that period. Sessions use the `sessionGapMinutes` rule, as everywhere else. The cut always lands on a session start, so no session is cut in half, and the last training event is more than the session gap before it. Events before the cut train; events at or after it test. A per-trader period, rather than one calendar date for everyone, gives every trader a test window whatever their dates.
2. **Churn caveat.** The active period ends at the trader's last event, so every trader is active through their whole test window by construction. The twin is not tested on churn: whether a trader stops coming back is outside this validation. The output and the model card say so.
3. **Too-small windows give null, never a number.** A trader needs at least `minTrainSessions` (2) training sessions, `minTestSessions` (3) test sessions, `minTestTrades` (10) test trades, and `minTestDays` (1) test days. Otherwise they get `eligible: false` and a reason, and no metric. The day minimum is there because the simulator starts its first session at a uniform time within 24 hours of its start, so a shorter window can't be simulated fairly. A trader the twin can't simulate, or with no estimated `baseStake`, is listed as not compared, with the reason. An ineligible trader's events before the cut, or every event when there is no cut, still go into the fit, so they inform the priors.
4. **One fit, per-trader simulation.** `estimateTwins` runs once on every trader's training events, with the caller's data label and `behaviorOptions`. Each trader is then simulated on their own, from their cut, for their test window length in days, starting at their last observed training `balance_after` (`lastObservedBalances`). Without balance fields the starting balance is 0, with the session-start deposit rule. `simulateTwinV2` takes one start and one horizon for everyone, so the validation calls `prepareSimulation` and `simulateReplicate` per trader. Replicate seeds don't depend on which other traders are simulated (ADR-012 point 8), so this equals a batch run; a test checks it. Runs go replicate by replicate across traders. Each run's events are reduced to the metrics and dropped at once, so memory stays flat. `simulate.mjs` is unchanged.
5. **Shared definitions.** Observed test events, training events, and every model's simulated events go through one function, `holdoutEventMetrics`, built on `buildBehaviorObservations` and `metricsFromEvents`. Every stake is divided by the training fit's estimated `baseStake` on every side. In-simulator metrics use each run's drawn `baseStake` and are never compared with event-derived values.
6. **Observable only.** Only quantities real event data shows are compared. Forced stops, refuel deposits, and stop causes are simulator decisions. The calibration check (ADR-012 point 13) took them from the generator's truth file, which a validator for real data can't do.
7. **Metrics** (`HOLDOUT_METRICS`). Each has a sample (one value per trade, session, or gap) and a per-trader statistic.
   - Stake after a loss and stake after a win: the stake on the trade after a realized loss or win in any session, divided by the training `baseStake`. Per trader: the median.
   - Their difference: the median after a loss minus the median after a win (signal 1's lossMinusWin), one value per trader.
   - Trades per session: session length in trades. Per trader: the mean, `metricsFromEvents`' `tradesPerSession`. Session length in trades and trades per session are one quantity, so they are one metric.
   - Session minutes: first to last event of each session with a trade. Per trader: the median.
   - Within-session inter-trade time, in minutes. Per trader: the median.
   - Deposits within `refuelWindowMinutes` after a realized loss, counted in the session each deposit falls in. Per trader: `metricsFromEvents`' `depositsAfterLossPerSession`.
   - Idle minutes between sessions: a diagnostic. It is reported but not scored, so the session-timing shape is visible without deciding the verdict.
   A missing realized outcome stays unavailable: the trade after it is in neither stake sample.
8. **Quantiles, bands, and KS without p-values.** For each metric, the observed p10, p25, p50, p75, and p90 of the pooled test sample are compared with bands. A band is the 10th to 90th percentile, across replicates, of each replicate's pooled quantile. The two-sample KS statistic D compares the pooled observed sample with the pooled simulated sample of the first `ksReplicates` (50) replicates; the cap keeps memory bounded. The simulated sample pools many replicates, so it is far larger than any real one, and a p-value would be meaningless. We report D as a distance and read it against a tolerance. Ties are handled by stepping both empirical CDFs past every copy of a value before taking the difference. That is the exact supremum for step functions, so D is exact for discrete metrics. Its null distribution is not the continuous one, which is one more reason for no p-value.
9. **Per-trader calibration.** A simulated model's point for a trader is the median of the trader's per-replicate statistic, and its band runs from the 10th to the 90th percentile. At least half the replicates must have a value. Calibration is the share of traders whose observed test statistic lies inside the band, with `simulation-calibration.mjs`'s rule (`bandCoverage`, slack 1e-9). The nominal share is 0.8. Count metrics (trades per session, deposits after a loss) have many ties and over-cover, so they are flagged and get their own tolerance, where only the floor binds.
10. **The models.**
    - twin: twin-0.2.1, fitted, uncertainty on.
    - baseline-0.1: `simulateBaseline` on `buildTwins(buildSignals(training events))`, through an adapter (point 11).
    - naive-0.1 (point 12).
    - truth: SYNTHETIC only, the generator's true parameters as point masses (`truth-twins.mjs`), uncertainty off. It is the best this model shape can do, so it separates estimation error (the truth reference is within tolerance and the twin is not) from model misspecification (neither is). Each metric's `diagnosis` says which.
11. **The baseline-0.1 adapter.**
    - **Shape.** baseline-0.1 events have their own shape (`occurredAt`, `stakeAmount`, `realizedResult`, `amount`), a hard-coded start at 2026-01-01T12:00Z, sessions at fixed hours, and no balances. The adapter maps them to the analytical schema with a fresh `event_id`, the trader token, `venue_id` `simulated-baseline-0.1`, and `source_row_number`, and drops `marketType`.
    - **Timing.** It shifts every event by (cut − that start), so the baseline's first session lands on the cut. It runs for max(1, test days) days, because its day offsets are `horizonDays` − 1 and a shorter horizon would place events before the cut.
    - **Overlapping sessions.** Its sessions sit at fixed hours, so a long session can run into the next one, and the event data then sees one session. We keep what its events say.
    - **Replicates** vary its seed: `stableSeed(seed:baseline-0.1:traderToken:replicate)`.
12. **The naive model (naive-0.1).** It repeats each trader's training values, with no dependence on the last outcome.
    - **Point prediction.** For each trader and metric, it is the same per-trader statistic computed on the trader's training events with the same definitions. Stake after a loss and stake after a win are both the median of every training stake divided by the training `baseStake`, and their difference is 0.
    - **Distribution.** The pooled training samples, honestly defined: every training stake for both stake metrics, and a 0 per trader for the difference. It has no band, so it gets no calibration.
    - **Why it matters.** On a stationary population, repeating the training values is a strong baseline for metrics that don't depend on the last outcome. A twin that only matches it adds nothing there.
13. **"Beats".** On one metric, the twin beats a comparator when both of these hold:
    - Its median absolute point error is below the comparator's × (1 − `errorMargin`). The error is computed on the paired set: traders with an observed value and a point from the twin, baseline-0.1, and naive-0.1.
    - Its KS D is below the comparator's D − `dMargin`.
    When only one of the two can be computed, that one decides. Overall, the twin beats a comparator when it beats it on more than `beatsShare` of the scored metrics they were compared on. **The twin earns a claim only if it beats both baseline-0.1 and naive-0.1.** When it doesn't beat one on some metric, that is reported as a finding (`summary.overall.findings`). The definitions and tolerances are not changed to make it pass.
14. **Tolerances and pass/fail** (`HOLDOUT_TOLERANCES`, set before any result was seen).
    - **Calibration** passes when coverage is within [0.65, 0.95] for continuous metrics, or within [0.65, 1] for tied ones.
    - **Distribution** passes when D ≤ 0.1.
    - **Margins**: `errorMargin` and `dMargin` are 0. `beatsShare` is 0.5, a strict majority.
    - **A metric passes** when its calibration and distribution pass and the twin beats both comparators on it.
    - **Overall pass** needs the claim, plus calibration and distribution passing on at least `passShare` (all) of the scored metrics.
    - `summarizeHoldout(result, tolerances)` is pure, so pass/fail can be recomputed with other tolerances without simulating again.
15. **Labels and provenance.** Every output carries:
    - the data label (SYNTHETIC, OBSERVATIONAL, or CUSTOMER);
    - the holdout, model, simulator, behavior, baseline, and naive versions;
    - the seed and the replicate counts;
    - the split rule and the churn caveat;
    - the assumptions list.
    Labels from the simulator are kept: all-cause stops and proxy refuel on the no-balance path, which is closest to what we expect from Sporttrade, and traders without a money model. On SYNTHETIC data, the known shape differences between the simulator and the generator (ADR-012 point 7) are attached to the metrics they affect. One is idle time between sessions. The other is deposits after a loss, which a short simulated idle time can add to. They are reported, not tuned away. A truth reference is refused for any other label.
16. **The OBSERVATIONAL hook.** `runObservationalHoldout(events, options)` runs the validation with the OBSERVATIONAL label, on events already in the analytical schema, without a truth reference. Loading the Polymarket public data and mapping wallets to events is **not wired**. `OBSERVATIONAL_HOOK` says so, and `npm run twin:holdout -- --observational` stops with that note.

Reason: The twin is only worth simulating policies on if it predicts a trader's later behavior better than simpler models. That has to be tested on data it wasn't fitted to, against baselines that are easy to beat for the wrong reasons (baseline-0.1) and hard to beat for the right ones (the naive model on a stationary population). Shared event-level definitions make the observed and simulated sides comparable. Keeping to observable quantities means the same validator runs on customer data. The truth reference tells a fitting problem from a model-shape problem.

Consequences:

- Validation numbers (coverage, D, errors, pass/fail counts) stay in test thresholds and gitignored output. They never appear in docs, the README, or commit messages.
- Results on CUSTOMER data are customer-derived and stay out of the repo, like the fit.
- The validation doesn't test churn, drift between the training and test periods beyond what the data shows, or responses to policies (there is no intervention data).
- Cuts differ by trader, so one trader's training period can overlap another's test period in calendar time. Shocks common to all traders, such as a market-wide event, are not held out.
- Training ends at a session boundary. A refuel deposit that would open the first test session within `refuelWindowMinutes` of the last training trade is not in the training data. This can't happen on the synthetic generator's data, whose minimum idle time exceeds the refuel window; on real data it can. A fix would need a per-trader observation end in `estimateTwins`, which takes one for the whole dataset.
- Prompt 7's report reads `summary` (pass/fail, "beats", findings) and `metrics` (quantile bands, D, calibration, point errors).

## ADR-015: Evidence report v2 (report-0.2.0)

Decision: `buildReportV2` in `src/engine/report-v2.mjs` builds one JSON report from one dataset, its twin fit, its held-out validation, and one policy sweep. `renderReportV2Html` renders that JSON, and only that JSON, as one self-contained HTML page. The six sections come in a fixed order: data and fields, population behavior, twin validation, policy trade-off, which traders are most affected, and assumptions and limits. `npm run demo` builds it from a SYNTHETIC behavioral population (`src/synthetic/report-demo.mjs`). The report-0.1.0 functions (`buildReport`, `renderHtmlReport`) are kept for comparison.

1. **Report output is local only.** The validation section contains held-out evaluation results: calibration coverage, KS distances, point errors, and pass/fail. CLAUDE.md keeps model evaluation metrics in gitignored local output. So `demo/output/` is now gitignored, and the old report-0.1.0 demo files are no longer tracked. A report built from CUSTOMER data is customer-derived and stays out of the repo, like the fit.
2. **No trader token.** Neither the JSON nor the HTML contains a trader token. Section 5 groups traders by archetype (SYNTHETIC only, when there are at least two) or by parameter range:
   - Chase coefficient: below 0.8, 0.8 to 1.25, and 1.25 or more. The 1.25 edge is the chase-episode line.
   - Stop pattern: down_large ÷ flat stop hazard below 1.5, 1.5 to 3, and 3 or more.
   A group with fewer than `minGroupSize` (5) traders is suppressed.
3. **Statements come from the data.** The chase statement says "most traders scale back and a minority chase" only when the estimates show it. Otherwise it says the data's actual direction. It also counts the traders whose 90% interval is entirely above 1. The stop and refuel statements work the same way, and a proxied refuel trigger is named as proxied.
4. **Section 5 uses one cell per policy.** That cell is the middle sweep setting with every response assumption at its default. Within each group, the report shows the median and the 10th to 90th percentile across traders of each trader's median harm reduction and activity retained. It also shows the group mean of each trader's mean paired change in net loss, and how many traders the policy reached. Many runs never trigger a policy, so median effects are often 0. When the largest group medians tie, the statement says no group stands out rather than naming one.
5. **Charts.** All charts are inline SVG with a visible title and an accessible title and description. There are no scripts and no external resources. The trade-off chart has one panel per swept response assumption, one series per value of it, and a point per policy setting. Each point has 10th to 90th percentile bars on both axes. A reference line marks harm reduction = 1 − activity retained, where a policy that only cuts activity would sit.
6. **No accuracy headline.** The report says "calibration coverage", "KS distance", and "point error", and states that validation is evidence about the model on this data, not an accuracy claim. A test checks that "accuracy" appears only in such denials and that no AUC or p-value appears.
7. **Labels must agree.** The fit, holdout, and sweep must carry the same data label and model version, or the build throws. The banner and the plain-language assumptions change with the label.

Reason: The report is what a design partner reads. It has to show what the data supports, how well the twin held up against simpler models, and what each policy result depends on, without exposing a trader or overstating a simulation.

Consequences:

- `npm run demo` now takes about a minute at its default scale. Flags scale it down.
- The repo no longer carries a committed demo report. Anyone who wants to see one runs `npm run demo`.

## ADR-016: Local intake for a raw venue export (intake-0.1.0)

Decision: `npm run intake` (`scripts/intake.mjs`) takes a raw CSV, JSON, or JSON Lines export to analytical events and then to report v2, on the user's machine, with the commands `profile`, `map`, `validate`, `readiness`, `run`, and `fields`. The logic lives in `src/intake/` (`source`, `pii`, `values`, `profile`, `map`, `validate`, `readiness`, `pipeline`, `fixture`), each with its own version string, so the CLI and the tests run one code path. The steps for Sporttrade's file and the config reference are in `docs/SPORTTRADE_INTAKE.md`.

1. **No raw values, ever.** No command prints or writes a raw identifier or a PII-looking value.
   - Profile shows masked shapes (letters become `A`, digits `9`), lengths, character classes, types, null rates, counts, and the date range of unflagged timestamp columns. PII-flagged columns show no shapes.
   - Drops and fixes are counts with reasons and at most five row numbers. Unknown type values are reported by shape.
   - Errors name columns, fields, and rows, never cell contents.
   - The one opt-in exception is `profile --categories`, so event-type codes can be read. It shows the distinct values of an unflagged column with at most 25 of them, each only if it occurs at least 5 times and has no 3-digit run or `@`.
2. **Tokenization.** A raw trader ID becomes `tr_` plus the first 16 hex characters of HMAC-SHA256(salt, trimmed ID). A mapped source row ID becomes `ev_` plus 20 hex of HMAC-SHA256(salt, `event_id:` + ID). Without one, `event_id` is `row_<line>`. So no raw source identifier reaches `events.json` or anything after it. Two IDs whose tokens collide stop the run.
3. **The salt.** It comes only from `PLAYMIND_TOKEN_SALT`, which `npm run intake` may load from a local `.env` (`--env-file-if-exists`). `.env.example` lists the name with an empty value. `map` and `run` refuse to start without it, or with fewer than 16 characters, and there is no default. The salt is never in a config, an output, or a message. One salt per customer keeps tokens stable across runs. Losing it breaks linkage to earlier runs, which is acceptable: nobody can reverse tokens without it either.
4. **PII rules.**
   - Direct PII is flagged by header: validate.mjs `PROHIBITED_FIELDS`, plus email, phone, address, birth date, government ID, IP, fingerprint, and person-name patterns, with camelCase and spaces normalized.
   - It is also flagged by value shape: any email-shaped value, or a majority of phone-, IPv4-, or person-name-shaped values.
   - A mapped column with a PII flag is rejected, even as the trader ID. A column whose header names an account or person may only be the trader ID column. Unmapped columns are dropped and listed by name.
   - `account_id`, `customer_id`, and `unmasked_account_id` are prohibited in analytical events. In a raw source they are the ID to tokenize, so they are flagged as raw identifiers, not rejected.
5. **One prohibited list, one normalization.** `validate.mjs` `PROHIBITED_FIELDS` was tightened to the forbidden headers of `src/lib/ingestion.ts`. It gained `full_name`, `first_name`, `last_name`, `username`, `user_name`, `customer_name`, `email_address`, `ip`, `account_id`, and `customer_id`. Nothing was removed from either list.
   - Prompt 9 closed the gap this point used to record. `parseTokenizedCsv` only trimmed and lowercased headers, so `Email Address` got past the upload path while intake rejected it. It now checks forbidden headers with `normalizeHeader`, the rule `validate.mjs` `normalizeField` uses: trim, lowercase, whitespace to `_`. Required columns still match after trim and lowercase only (`Event ID` does not count as `event_id`), so the change only tightens.
   - `test/intake-validate.test.mjs` checks that the lists agree, and that the upload path, `validateEvents`, and intake give the same verdict on every listed name and its spaced, cased, and padded variants.
   - Intake still rejects a superset: it also splits camelCase and maps punctuation to `_` (`EmailAddress`, `email-address`). A test pins that difference, so a later change to either side shows up.
6. **Labels.** Every command needs `--label` (SYNTHETIC, OBSERVATIONAL, or CUSTOMER), and a label in the config must agree. Every output carries it: JSON files at the top level, `readiness.md` in its title, the report in its banner. A CUSTOMER run prints a reminder that its outputs are customer-derived. The fixtures are SYNTHETIC.
7. **Where outputs go.** By default, `data/output/<run-name>/`, which is gitignored. A run name must be a plain name, so a default run can't write outside `data/`. Any other directory needs an explicit `--out`. A CUSTOMER run also refuses an input file, mapping config, or `--out` inside the repo but outside `data/`.
8. **Readiness is derived, not restated.** `assessReadiness` reads `requires`, `anyOf`, `voluntaryNeeds`, `proxyFor`, and `fallback` from `BEHAVIOR_SIGNAL_DEFINITIONS` and `TWIN_PARAMETER_DEFINITIONS`. Two engine rules are stated in the module rather than taken from the tables: which event types each field is read on (the scopes report v2 uses), and that balance fields count only for traders with both of them on every trade. The field tiers in `docs/SPORTTRADE_INTAKE.md` come from `fieldAskList()`, and a test fails if the doc drifts.
9. **Cleaning a raw dump.** These are handled and counted: blank rows, exact duplicate rows (after trimming), rows with extra non-empty cells, comment lines before the header, stray whitespace, null markers (`NULL`, `NaN`, `N/A`, `\N`, `None`), case and padding in type values, thousands separators, accounting parentheses, and currency symbols. Missing realized results stay null, never 0. Timestamps without an offset are read in the configured time zone and written as UTC ISO.
10. **Fixtures.** `scripts/build-intake-fixtures.mjs` builds `test/fixtures/intake/ledger-export.csv` from the behavioral generator: 24 traders, no balances, some missing results, cents, UTC, a raw account ID column, and dump artifacts. `ledger-export-pii.csv` is deliberately bad. A test rebuilds both and compares them with the committed files.

Reason: Sporttrade's export will be a raw dump with unknown columns and no market detail. The first look at it must not leak an identifier. The mapping must state its assumptions (units, time zone, signs) instead of guessing them. The ask list we send back must follow from what the model actually needs.

Consequences:

- The mapping config for a real export holds real column names and type codes, so it is customer data and lives under `data/`.
- Exact-duplicate removal assumes identical rows are export artifacts. A source without a row ID, where identical rows can be real, needs `dropExactDuplicates: false`.
- Value-shape PII detection is heuristic. A PII column with unusual formatting can pass the value checks. The header rules and a human review of the mapping are the other guards.
- Event types mapped to `restriction_event` or `self_exclusion_event` are carried through, but no signal or parameter reads them yet.
